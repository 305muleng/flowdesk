# 统计缓存与到期提醒设计

## 使用范围

FlowDesk 面向小型团队的项目执行与交付验收。统计缓存用于项目看板，到期提醒用于异步催办；两者采用 Redis，但处理的问题和一致性要求不同。

本项目保留这两项方案，用于实现并验证缓存失效、事务边界和异步消息恢复。没有以生产访问量或性能提升数字作为选型依据，也没有把它们视为唯一可行方案。

## 项目任务统计缓存

### 为什么缓存统计

项目详情和看板会重复读取同一项目的任务数量及执行进度。它们属于聚合展示数据，允许短暂延迟，适合使用 Cache-Aside：读取缓存，未命中时查询数据库并回填。

缓存命中仍然检查当前账号、项目成员关系和项目是否存在，只省略任务统计聚合查询。缓存不保存访问权限，不能因为命中缓存而跳过授权。

项目验收、成员退出等业务约束使用数据库查询，不使用缓存统计决定能否执行。个人任务汇总接口也没有加入此缓存。

### 读写流程

1. `ProjectTaskSummaryService.getTaskSummary` 检查权限及项目存在性。
2. `ProjectTaskSummaryCache.get` 读取当前项目统计。
3. 未命中时执行 `TaskMapper.selectTaskStatusCounts`，构造统计结果并回填。
4. Redis 读取失败时查询数据库，本次不再尝试回填；后续请求仍会重新尝试访问 Redis，当前没有跨请求熔断。
5. 影响统计的写操作在事务提交后删除缓存；事务回滚时不删除。
6. 第一次删除后登记延迟补删，降低旧查询在删除之后回填旧值的影响。

没有采用直接更新缓存，是为了让数据库保持唯一业务数据来源，避免每条状态变化路径分别维护计数和缓存更新顺序。

### 一致性边界

延迟补删可以覆盖部分旧值回填窗口，不保证强一致。旧查询晚于第二次删除才完成、Redis 删除失败、进程退出或延迟任务被拒绝，都可能留下旧统计。

TTL 为 60 秒，从每次缓存写入时计算。如果旧请求更晚回填，不能承诺“数据库变更后最多 60 秒一定一致”。延迟任务保存在当前进程内，也没有持久化补偿。

延迟补删当前配置为 10 秒，是可调整的实验参数，没有通过线上请求耗时分布推导。它不是查询一定能在 10 秒内结束的保证。

读取失败可回退数据库，但要先等待 Redis 连接或命令失败；提交后的首次删除也是同步执行。因此，这里的容错表示保留数据库查询与业务提交结果，不表示 Redis 故障完全不影响响应时间。

直接查询数据库同样适合小规模场景。本项目保留缓存来处理重复聚合读取，并验证失效和故障分支；没有声称缓存已经解决高并发瓶颈。

## 任务到期提醒

### 为什么异步处理

提醒可以晚于任务变更产生，不需要阻塞用户等待发送。后台独立扫描到期时间并处理提醒，用户操作只同步相关计划。

Redis Streams 提供消费组、待确认消息和显式确认能力，能够支持中断后的接管及重试。项目复用 Redis，不额外部署独立消息中间件。

数据库保存提醒计划和事件，Redis 负责传输事件编号。数据库直接轮询并处理事件也是可行替代方案；当前方案增加了队列环节，用于实现可确认、可重投的消费流程。生产和消费仍运行在同一个应用进程内，尚未独立部署，也没有验证独立扩缩容。

### 计划、事件与通知的职责

- `task_reminder_plan` 保存任务截止时间、执行人和版本。截止时间或执行人变化时，计划与任务变更在同一事务内更新。
- `TaskReminderService.planTask` 由后台扫描触发，在自己的事务中复核当前状态、同步计划并生成到期事件。提醒事件并非在每次任务写入时立即生成。
- `task_reminder_event` 保存事件状态、重投时间及失败信息，唯一约束限制同一任务、计划版本、提醒种类只有一个事件。
- Stream 消息只包含事件编号。消费者重新查询数据库，避免使用消息中的旧执行人或截止时间直接发送。
- 消费时按项目、任务、计划、事件的顺序加锁，检查状态、版本、时间及接收人。
- 通知写入和事件完成在同一数据库事务中提交，事务代理返回后才确认 Redis 消息。

提醒仅针对进行中项目的 TODO / IN_PROGRESS。每个计划版本有临期、逾期两类提醒，各自最多成功写入一次通知；调整计划后可以产生新版本的提醒，已经发送的通知保留为历史。

### 故障如何处理

| 情况 | 当前处理 |
| --- | --- |
| Redis 暂时不可用 | 数据库事件仍保持待处理，按持久化时间重投；故障期间不能保证及时发送 |
| 发布成功但生产者中断 | 事件尚未完成，之后可能再次发布，由消费端去重 |
| 通知写入后、事务提交前失败 | 通知与事件完成一起回滚，事件仍可重试 |
| 数据库提交成功但消息确认失败 | 再次消费时读取到事件已完成，不重复写入通知，再尝试确认 |
| Stream 丢失或消息被裁剪 | 数据库中尚未完成的事件仍有资格重投 |
| 任务已提交、取消，或计划已变化 | 复核后将旧事件作废，不继续催办 |
| 执行人账号不可用 | 复核并回退到当前有效项目负责人，没有有效接收人则保留事件等待重试 |

通知去重依靠数据库锁、事件完成状态及事务，不能归因于 Streams 天然提供恰好一次投递。该保证限定于本数据库中的提醒通知写入，不自动适用于邮件、短信等外部副作用。

### 参数与运行边界

待确认消息空闲达到 60 秒后可以接管。空闲不代表原消费者一定已经停止，慢处理也可能被再次领取；数据库中的锁和事件状态负责抵挡重复处理。60 秒是当前恢复策略参数，没有基于生产耗时分布验证。

重投间隔逐渐增加，最长 5 分钟；这个上限针对重投间隔，不是提醒必定在 5 分钟内送达。当前没有按重试次数丢弃事件，也没有死信处理和长期事件归档策略。

专用 Stream 只有一个业务消费组，确认后删除消息正文，业务结果继续保存在数据库。不能直接增加需要读取同一消息的第二个业务消费组而沿用现有删除策略。

## 对应验证

| 内容 | 对应测试 | 验证方式 |
| --- | --- | --- |
| 缓存命中、聚合结果、读取失败后不回填 | `ProjectTaskSummaryServiceTest` | Mock 依赖，验证业务分支 |
| 提交后删除、回滚不调度、调度拒绝及删除失败 | `ProjectTaskSummaryDelayedEvictionTest` | Redis、调度器及事务替身 |
| 实际事务提交或回滚对缓存的影响 | `ProjectTaskSummaryCacheTransactionTest` | Spring 事务与专用 Redis |
| 预约重投、确认失败、退避及扫描失败 | `TaskReminderJobsTest` | 调度逻辑及依赖替身 |
| 建组、读取、接管、确认及删除顺序 | `RedisReminderStreamTest` | Redis 操作替身 |
| 回滚、重复消费、待确认消息接管、Stream 丢失补发、计划失效 | `TaskReminderIntegrationTest` | 专用 MySQL / Redis |
| 截止时间调整后的版本变化、旧事件失效及通知历史保留 | `TaskWorkIntegrationTest` | 实际事务与专用数据库 |

测试源码证明覆盖意图，执行结果以对应运行报告为准。重建消费者对象不等于重启应用进程；依赖替身失败不等于实际断开 Redis 服务。本文没有把这些验证范围混用，也不将测试数量当作生产吞吐能力的证据。
