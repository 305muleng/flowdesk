# FlowDesk

FlowDesk 是一个面向小型研发团队、具有交付验收要求的项目管理系统，覆盖项目创建、成员协作、任务执行、成果审核、项目验收与归档。

项目用于 Java 后端工程实践和实习、校招准备，重点展示业务建模、权限控制、事务并发、缓存一致性、异常处理和测试能力。

## 业务流程

```text
创建项目
  → 邀请成员、规划任务
  → 启动项目
  → 执行任务、提交成果
  → 项目负责人审核
  → 提交项目验收
  → 系统管理员审核
  → 完成并归档
```

项目验收被驳回后，可以继续整改并再次提交。成员退出、负责人转让、站内通知和操作审计为主流程提供支持。

密码哈希使用 Spring Security Crypto 的 BCrypt 组件；认证与授权由 JWT、拦截器和业务权限检查实现。

## 角色与权限

系统角色和项目角色分开管理。

| 角色 | 职责 |
| --- | --- |
| 普通用户 `USER` | 创建项目、接受邀请，在不同项目承担不同职责 |
| 系统管理员 `SYSTEM_ADMIN` | 兼任平台管理和最终交付验收人，不自动拥有普通项目管理权限 |
| 项目负责人 `PROJECT_MANAGER` | 管理本项目成员、任务、审批、交付及生命周期 |
| 开发人员 `DEVELOPER` | 执行任务、提出任务申请、参与讨论和申请退出 |

项目角色属于用户与项目之间的关系。同一个用户可以是一个项目的负责人，同时是另一个项目的开发人员。

后端根据当前账号和项目成员关系校验权限。前端菜单和按钮用于引导操作，不代替后端鉴权。

## 主要功能

### 项目管理

- 创建项目，创建者自动成为项目负责人。
- 查看参与项目、项目详情、成员及操作记录。
- 当前项目负责人可在准备中、进行中编辑名称、描述、目标和预计结束时间；沿用创建时的必填规则，描述、目标及预计结束时间可清空。
- 启动、取消、提交验收和归档。
- 项目取消后冻结正常推进，但不批量修改正式任务状态。

项目状态：

```text
PREPARING → IN_PROGRESS → PENDING_ACCEPTANCE → COMPLETED → ARCHIVED
                              │
                              └─验收驳回→ IN_PROGRESS

PREPARING / IN_PROGRESS → CANCELLED
```

待验收期间暂停日常修改，完成、归档和取消后限制业务写操作。

### 任务与任务申请

- 项目负责人创建正式任务，标题、描述和目标均为必填，可设置任务负责人、优先级和截止时间。
- 开发人员提出任务申请，标题、描述和目标均为必填；负责人批准后生成正式任务。
- 任务支持开始、提交、审核、取消、评论和提交历史查询。
- TODO 状态允许重新分配任务负责人。
- 当前项目负责人可在准备中、进行中编辑 TODO 任务的标题、描述、目标、优先级和截止时间；标题、描述、目标及截止时间必填，截止时间须晚于当前时间。负责人仍通过独立分配入口修改。
- 项目负责人也可以承担并审核自己的任务；最终交付由系统管理员验收，不将任务审核视为独立质量认证。
- 进行中项目的 IN_PROGRESS 任务可由负责人单独调整截止时间，必须填写原因并提供原截止时间；旧请求返回冲突，不覆盖新调整。操作审计记录原时间、新时间和原因，提醒计划随之更新。
- 个人待办、到期及逾期提示只面向进行中项目的 TODO / IN_PROGRESS 任务；REVIEW 单独表示等待审核。准备中任务属于计划工作，结束项目中的任务保留原状态供历史查询。
- 我的任务默认显示当前项目，可切换历史或全部项目；列表同时展示项目状态，查询仍受当前成员权限约束。

任务状态：

```text
TODO → IN_PROGRESS → REVIEW → DONE
                       │
                       └─驳回→ IN_PROGRESS

TODO / IN_PROGRESS → CANCELLED
```

审核驳回时，如果原任务负责人账号已不可用，任务回到 TODO 并清空负责人，等待重新分配。

### 成员管理

- 邀请普通用户加入项目，支持接受、拒绝和过期判断。
- 开发人员申请退出，由项目负责人审批。
- 项目负责人可以移除符合条件的开发人员。
- 负责人转让需要密码确认，并由目标用户接受。
- 转让时，原项目负责人可以留任开发人员或退出项目。

退出或移除成员前检查未完成任务。成员关系停用后保留历史任务归属和贡献，不直接删除历史关系。

### 账号禁用与任务交接

- 管理员可启用或禁用账号。
- 仍负责特定状态项目的账号不能直接禁用，页面按项目说明转让、验收处理或归档要求。
- 禁用不自动删除成员关系，也不自动重新分配任务。
- 禁用提交后，向相关活动项目的负责人尽力发送站内通知。
- 项目成员页可定位禁用成员承担的未完成任务。
- 对禁用账号承担的 IN_PROGRESS 任务，项目负责人可以填写原因，交接给有效项目成员。
- 交接后任务回到 TODO，保留内容、评论和提交历史，并记录审计。
- 重新启用账号不会自动撤销已经完成的交接。

通知失败不会回滚已提交的禁用操作。当前没有持久化通知重试或通知必达保障。

### 项目交付与验收

提交验收前要求：

- 项目处于 IN_PROGRESS。
- 没有 TODO、IN_PROGRESS、REVIEW 任务，且至少有一项 DONE 任务。
- 没有 PENDING 任务申请。
- 提供验收说明及至少一个代码仓库、部署或文档链接。

管理员通过后项目进入 COMPLETED；驳回后回到 IN_PROGRESS，整改后生成新一轮验收记录。

零任务或全部任务取消的项目不能提交验收。部分取消的任务及其原因在验收中展示；驳回后通过新建整改任务继续推进，原任务和历轮验收记录保留。

验收详情包含本轮提交及审核记录；新提交展示该轮保存的项目资料、交付链接、任务统计、取消任务和成员贡献，数据来源按下述规则标注。

新提交的验收记录保存独立的V1提交快照，包含项目资料、交付链接、任务统计、成员贡献及取消任务清单。驳回整改后重新提交会新增记录，历史轮次仍显示各自提交时的数据。当前项目状态和本轮审核结果继续正常更新。

两个快照字段均为NULL时，详情明确标注“未保存提交快照，展示当前数据”，不回填伪造历史。快照内容损坏或版本不支持时返回明确错误，不用当前数据替代。完整详情仍仅管理员可读，普通成员权限不变。外链内容本身没有归档。

### 两种统计口径

| 指标 | 公式 | 含义 |
| --- | --- | --- |
| 执行进度 | `DONE / (总任务数 - CANCELLED) × 100%` | 有效工作范围完成了多少 |
| 任务完成占比 | `DONE / (DONE + CANCELLED) × 100%` | 已结束任务中，完成而非取消的比例 |

分母为零时均返回 0。

例如 8 个任务完成、2 个取消，执行进度为 100%，任务完成占比为 80%。后者按任务数量计算，不是管理员审批通过率，也不代表实际工作量或交付质量。

### 请求关闭与过期

- 验收通过：关闭仍有效的待处理邀请、退出申请和负责人转让。
- 项目取消：额外关闭待处理任务申请。
- 关闭使用 `CLOSED`，保存关闭时间和原因。
- 已处理或已过期记录不被覆盖。
- 待验收期间只暂停操作；驳回后，未过期且符合条件的请求可以继续处理。
- 项目结束与请求关闭位于同一事务。
- 不追溯关闭以前已结束项目的遗留请求。

查询时识别过期，操作时重新检查有效期。CLOSED、用户撤回、拒绝和时间过期具有不同含义。

### 分页、筛选与统计

项目任务、我的任务、通知列表和项目操作记录使用后端分页：

- 默认每页 20 条，最多 100 条。
- 筛选在分页前执行，总数对应完整筛选结果。
- 项目任务支持范围、状态、任务负责人及仅未完成筛选。
- 我的任务支持状态和标题关键词筛选。
- 通知支持分类及已读筛选。
- 相同时间使用 ID 作为第二排序条件。
- 筛选变化重置页码，数据减少后处理空页回退。

项目进度使用项目汇总接口，个人统计使用当前用户汇总接口，不从当前页计算全量统计。

通知未读总数与“全部已读”覆盖当前用户的全部通知，不受当前页或分类限制。

### 通知与审计

站内通知关联邀请、申请、任务、验收及成员事件，支持已读处理和历史跳转。

已读不表示关联业务已经处理。历史记录能否查看、能否操作，仍由对应业务权限和状态决定。

操作审计保存操作者、对象、动作、修改前后信息和时间，用于追踪关键业务变化。项目和任务资料编辑与修改前后审计记录位于同一事务；不会改写已保存的验收快照。操作记录页支持按时间、ID倒序分页查阅历史；项目详情展示最近30条，并可跳转查看该项目的全部记录。

## 后端设计

### 认证与权限

- BCrypt 保存密码哈希。
- JWT 标识登录用户。
- 请求拦截器读取当前账号状态及系统角色。
- Service 根据当前项目成员关系校验业务权限。
- 请求结束后清理 ThreadLocal 用户上下文。

退出登录当前清除客户端凭证，不提供服务端 Token 黑名单或会话吊销机制。

### 事务与并发控制

关键状态变化结合数据库事务、项目行锁和条件更新，协调任务写入、成员变更及项目验收。

条件更新检查预期状态或负责人，避免过期请求直接覆盖已经变化的业务结果。

请求关闭使用 MANDATORY 参与项目结束事务；禁用通知使用提交后本地事务事件，并以独立事务隔离各项目通知失败。

这些机制有不同的业务目的，不代表已经实现所有故障场景下的可靠投递或分布式事务。

### Redis 任务统计缓存

接口：

```text
GET /projects/{projectId}/task-summary
```

设计：

- 先校验项目权限和存在性，再读取缓存。
- Key：`flowdesk:project:{projectId}:task-summary:v1`。
- Value：任务统计 JSON，TTL 为 60 秒。
- 未命中时查询数据库并回填。
- Redis 读取失败时回退数据库，跳过本次回填。
- 影响统计的业务提交后删除缓存，回滚不删除。
- 使用延迟补删降低旧值回填的影响。

配置项：

```properties
flowdesk.cache.task-summary.second-delete-delay-ms=10000
```

当前 10 秒为实验配置，不是已论证的生产参数。

延迟补删不保证强一致；删除失败、进程退出、调度拒绝和更晚的旧值回填仍是边界。当前没有可靠补偿队列或跨请求熔断。

个人任务汇总接口为：

```text
GET /tasks/my/summary
```

只统计当前登录用户有权访问的任务，本接口当前不增加 Redis 缓存。

### 任务到期提醒（需显式启用）

提醒仅面向进行中项目的 TODO / IN_PROGRESS 任务：截止前24小时内一次、到期仍未提交再一次，不按天重复。REVIEW 不催执行人；优先通知当前有效执行人，无执行人或账号不可用时通知当前有效项目负责人。复用通知中心的“任务”分类与任务详情跳转。

`task_reminder_plan` 保存截止时间、执行人及计划版本；改变截止时间或执行人时，与任务变更同事务推进版本。定时扫描补齐历史任务和关闭模块期间的计划，并按当前时间生成 `task_reminder_event`。恢复时已逾期的任务只补逾期事件。每个计划版本的每种提醒最多生成一个事件；已经提交、取消或失效的消息不再催办。审核驳回后，若任务重新符合条件，可恢复同版本尚未发出的作废事件；成功发送的事件不会重置，已保存的通知仍是历史记录。

事件先落数据库，再投递到专用 Redis Stream。投递前持久化下次重投时间；Redis 暂时不可用、消息被裁剪或 Redis 数据丢失后，数据库中的待发送事件仍可再次投递。消费时按项目、任务、计划、事件顺序加锁，复核状态、版本和当前接收人；通知插入与事件完成在一个事务内提交，随后才确认 Redis 消息。重复投递依靠锁定后的事件完成状态去重，不宣称 Redis 提供恰好一次投递。

消费者使用消费组，定期接管超过60秒未确认的消息。失败记录事件编号与异常类型，重投退避最长5分钟，不因固定重试次数耗尽而丢弃。扫描按任务ID分批轮询，避免持续失败的少数任务占满所有批次。后台通知不伪造用户登录上下文，操作者为空。

启用方式：

1. 导入完整数据库结构 database/flowdesk.sql。
2. 启动后端前设置 `FLOWDESK_REMINDERS_ENABLED=true`，沿用已有 MySQL / Redis 连接配置；默认关闭，不访问提醒表或队列。
3. 未调整调度配置时，计划扫描30秒一次、投递5秒一次、消费1秒一次，每批最多100条。提醒是异步处理，时间不是硬实时保证。

维护者可查询 `task_reminder_event` 的 `state`、`attempts`、`last_error`、`next_publish_at` 定位积压；修复故障后等待自动重投，不提供公共重放接口。专用流 `flowdesk:reminders:stream:v1` 只有一个业务消费组 `task-reminders`，确认后删除正文，并限制保留长度；业务结果保留在数据库。长期事件归档和清理策略尚未实现，不应假定存储可无限增长。

本模块保留规则及故障分支的替身测试，另有 TaskReminderIntegrationTest 使用专用 MySQL/Redis 验证事务回滚、重复消费、消费组待确认消息重领、流丢失后的数据库补发及计划变更。重建消费者实例不等于实际重启整台服务器；整套浏览器流程和真实进程重启另行验证。现有邀请、审批、禁用账号等通知保持原有同步或本地事件方式，没有整体迁移到 Stream。

## 本地运行

### 环境

- Java 17。
- MySQL；当前结构导出自 MySQL 9.7.0。
- Redis；本地实践使用 Redis 8.2。
- Node.js 版本遵循 `frontend/package.json` 的 engines。
- Maven Wrapper 或兼容的本地 Maven。

以下命令以 Windows CMD 为例，在项目根目录执行。

Linux/macOS 使用 `bash ./mvnw` 替代 `mvnw.cmd`；前端命令相同。

### 数据库初始化

结构文件：

```text
database/flowdesk.sql
```

包含当前 15 张表和索引，包括任务统计覆盖索引及请求关闭字段，不包含业务数据。

在已选择的空数据库中执行。

若使用名为 mysql 的 Docker 容器，可以：

```bat
docker cp database/flowdesk.sql mysql:/tmp/flowdesk-schema.sql
docker exec -it mysql mysql -u root -p
```

在 MySQL 客户端中创建并选择数据库：

```sql
CREATE DATABASE flowdesk
    CHARACTER SET utf8mb4
    COLLATE utf8mb4_0900_ai_ci;

USE flowdesk;
```

然后在同一个 MySQL 命令行客户端中导入结构：

```text
SOURCE /tmp/flowdesk-schema.sql;
```

如果数据库已存在，先确认用途及内容，不直接继续导入。

使用本机 MySQL 时，在项目根目录导入结构：

```bat
mysql -h 127.0.0.1 -P 3306 -u root -p flowdesk < database/flowdesk.sql
```

注册接口只创建普通用户。首次系统管理员账号需要由环境维护者单独准备，项目不内置默认管理员密码。可先通过注册接口创建一个专用账号，在其尚未创建或加入普通项目时，由维护者核实账号身份后将系统角色设置为 `SYSTEM_ADMIN`。不要复用普通项目成员账号。

## 测试与实践记录

测试明确分为两层，避免普通检查依赖本机 MySQL/Redis，也避免把模拟测试称为真实数据库验证。

### 默认测试：不连接外部服务

在项目根目录运行：

```bat
mvnw.cmd test
```

默认只运行没有 `integration` 标签的测试，不需要数据库密码、Redis或应用密钥。包括业务判断、Web接口模拟、序列化、SQL契约及使用事务替身的测试；不能据此声称真实SQL、InnoDB锁或Redis已验证。

### 真实 MySQL/Redis 集成测试：显式启用

先准备专用测试环境并提供以下变量，不把实际凭据提交到仓库：

| 环境变量 | 用途 |
| --- | --- |
| `FLOWDESK_TEST_DB_PASSWORD` | 必填，专用测试数据库账号密码 |
| `FLOWDESK_TEST_REDIS_CONFIRMED` | 必须显式设为 `true`，表示已确认测试目标 |
| `FLOWDESK_TEST_REDIS_HOST` | 默认 `127.0.0.1`，仅允许 `127.0.0.1` 或 `localhost` |
| `FLOWDESK_TEST_REDIS_PORT` | 默认 `6379`，必须为有效端口 |
| `FLOWDESK_TEST_REDIS_DATABASE` | 默认 `15`，保护逻辑只允许DB15 |
| `FLOWDESK_TEST_REDIS_USERNAME` | 可选Redis认证用户名 |
| `FLOWDESK_TEST_REDIS_PASSWORD` | 可选Redis认证密码，按测试服务器实际配置提供 |

数据库固定为本地3306端口的 `flowdesk_test`，账号为 `flowdesk_test_user`，不能使用业务库或root账号。测试库通过 database/flowdesk.sql 初始化；测试命令不自动建表。

确认环境后执行：

```bat
set "FLOWDESK_TEST_REDIS_CONFIRMED=true"
mvnw.cmd -Pintegration test
```

此profile只运行标有 `@IntegrationTest` 的真实集成测试，普通测试仍需执行前一条命令。未启用profile时，集成测试被过滤而非已通过；启用后缺少环境确认或目标不符则明确失败，不静默跳过。

单独运行其中一类时仍需启用profile，例如：

```bat
mvnw.cmd -Pintegration -Dtest=FlowdeskApplicationTests test
```

保护分两步：刷新测试上下文前核对配置；用例准备数据前核对实际数据库名/账号，以及Redis连接实际选择DB15。测试只清理自身专用记录和精确Key，不执行FLUSHDB/FLUSHALL，不启停服务。执行真实集成测试期间避免其他程序同时写入测试库，以便判定残留。

测试专用配置使用 `@TestConfiguration`，在专门的测试中显式加载，不通过允许任意Bean覆盖来绕过装配问题。完整应用上下文测试同时核对没有加载专用测试配置、事务替身或替换版服务。

### 验证范围

普通测试覆盖业务判断、参数校验、映射和接口模拟；集成测试覆盖真实 MySQL/Redis、并发、事务、消息恢复及 HTTP 调用。
测试数量和运行结果以本次控制台输出及对应报告为准。Maven 报告位于 target/surefire-reports，连续执行不同选择集时可能保留其他用例的报告。

前端检查：

```bat
cd frontend
node --test tests/*.test.cjs
npm run build
```

项目已有本地合成数据、缓存命中/未命中、索引、故障及旧值回填实验，不作为生产流量或生产吞吐能力的证明。

## GitHub 自动检查

`.github/workflows/ci.yml` 在向 `master` 推送和创建、更新 PR 时运行，也支持在默认分支手动触发：

- 后端：独立 Linux 环境，Java 17，通过 Maven Wrapper 执行默认普通测试。
- 前端：独立 Linux 环境，Node.js 24，按锁文件安装依赖，运行前端测试、类型检查和生产构建。

CI 不提供业务或测试环境凭据，也不运行 `integration` profile。真实 MySQL/Redis 集成测试仍按前文说明显式执行；自动检查通过不代表浏览器验收、真实环境集成测试或部署通过。

工作流只授予读取仓库权限，第三方 Action 固定到已核实的官方提交；后续升级时核对上游版本和提交。
